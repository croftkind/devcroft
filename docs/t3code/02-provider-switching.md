# Provider switching and context handoffs

The app thread has one transcript and one workspace binding. Each provider contributes through its own native conversation. A switch changes the model selection on the existing thread, and subsequent execution chooses how to reuse or reconstruct the target provider’s state. The previous runs remain attributed to the instances that executed them. [App thread and run schemas](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/packages/contracts/src/orchestrationV2.ts#L472) · [Switch planning](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/ProviderSwitchService.ts#L55) · [Message dispatch](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L7031)

## Example

| App thread activity | Effect on native conversations |
| --- | --- |
| Runs 1–3 use Codex. | Codex conversation C1 contains its native work for those runs. |
| The user selects Claude and sends run 4. Runs 4–5 use Claude. | Claude starts L1 with a portable handoff built from eligible app history through run 3. The new request remains the run 4 prompt. |
| The user selects Codex and sends run 6. | When C1 is reusable and can fit the transfer, Codex resumes it and receives a delta drawn from eligible work since C1 last participated, here runs 4–5. |
| In a different outcome, C1 cannot resume. | The turn service can open a replacement Codex native conversation and use a bounded recovery handoff. The app thread and its transcript keep their existing identity. |

## Selection policy and execution

The server compares the current and target instance, model and options, continuation identity, workspace, and runtime mode. The target adapter classifies same-instance model changes with the available session capabilities. The transition policy can reuse a session, apply the model in session, restart and resume the same native context, create with a handoff, or reject the change. Continuation identity matters even within one driver. Two configured instances with different accounts or homes cannot be treated as interchangeable just because both use Codex. [Switch planning](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/ProviderSwitchService.ts#L55) · [Transition policy](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/ProviderSessionTransitionPolicy.ts) · [Instance identity](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/packages/provider-core/src/server/instanceIdentity.ts)

Instance changes and changes that release a session are rejected while an active run exists on the direct thread-mutation path. A model change that can stay in session has a separate path, including an optional effect to apply it to the live provider. On the message path, orchestration resolves the target provider thread and determines its history coverage. Queued starts also make a continuation decision and can hold the queue when a restart would replace a session with live background work. [Busy check and selection mutation](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L4621) · [Live selection effect](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L5492) · [Queued start and background work](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L2741)

For a cross-provider message, the orchestrator can look up a prior root provider thread for the target instance, within the current context boundary. It identifies the most recent eligible source run the target actually received and selects the missed eligible runs. A target with a native reference normally gets a delta. A fresh target uses a full-history strategy whose actual payload is bounded. If there is no uncovered history, no automatic provider handoff is needed. An explicit fresh-context run has its own context boundary. [Provider-thread lookup and delivery watermark](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L1502) · [Handoff strategy during message dispatch](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L8947)

## What crosses the boundary

A `ContextTransfer` identifies the source, destination, and relationship. A `ContextHandoff` carries the portable material and records its provider destination and delivery state. For a provider switch, source and destination app thread IDs can be the same. The persisted strategy name `full_thread_summary` describes the coverage strategy. The current provider handoff selects historical records deterministically and can preserve intact user and assistant messages, retaining role and original ordering. It prioritizes the last user message, last assistant message, and first user message before filling from recent items. Eligible activity can also carry compact descriptions. Started work from failed or interrupted runs can contribute. [Context schemas](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/packages/contracts/src/orchestrationV2.ts#L247) · [Handoff preparation](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/ContextHandoffService.ts) · [History selection](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/packages/provider-core/src/server/handoffBudget.ts#L223)

The budget accounts for available model capacity, known or estimated existing native usage, the current request, attachment allowances, and working room. The default initial history cap is 16,000 with a 1,024–64,000 configuration range. The calculation conservatively charges serialized text by UTF-8 bytes and bounds imported history separately from the prompt and its attachments. The exact live context capacity can still differ from the estimate. [Budget calculation](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/packages/provider-core/src/server/handoffBudget.ts#L14) · [Portable handoff guide](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/user/portable-handoffs.md)

The target receives role-attributed history and omission information. Omitted material remains readable in the canonical thread through MCP. Reasoning internals, native tool state, and old attachment payloads stay with their original runtime or storage. The user’s new prompt and its attachments are handled as the current turn. Codex can receive structured historical items via `thread/inject_items` when supported. The adapter can decline native injection, allowing attributed inline context. ## Failure and retry behavior

- **Ambiguous delivery.** Before injection, delivery is persisted as `pending` for the specific native thread. Success records delivered and omitted item IDs. A crash in between can leave delivery uncertain. The turn service can reconstruct a fresh native conversation to keep a retry from injecting the same material twice into the old one.
- **Resume or context-budget failure.** The turn service can test whether a fresh native conversation can fit the recovery handoff. A native thread held by another client is surfaced as busy, and a context-budget restart checks for pending background work before replacing the conversation. A request that still cannot fit surfaces an error.
- **Long-term reconstruction.** Because the app stores its own transcript, recovery can select app-visible material even when native continuity is unavailable. A native-only imported history has stricter recovery constraints because the provider may hold its sole copy.

For Devcroft, the core invariant is a stable app thread and an explicit record of what each native conversation received. Starting with a fresh target and a portable handoff is feasible. Returning-native resume and delta delivery add fidelity when an adapter can verify the native reference and the coverage watermark.
