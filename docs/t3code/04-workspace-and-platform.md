# Workspace and platform features

The same host that runs agents owns workspace identity, process state, and Git operations. Several T3 Code features depend on that shared context. This page covers features that affect the boundaries of a Devcroft redesign.

## Workspace, changes, and undo

**Thread launch.** A thread can run in the project folder, an existing worktree, or a new worktree. Thread launch resolves workspace preparation before provider execution and can surface preparation failures with the run. Workspace selection is independent of provider selection. Isolated children can use the same preparation path, beginning at the resolved base commit. [Launch service](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/ThreadLaunchService.ts#L69) · [Worktree settings](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/user/project-settings.md#worktree-location)

**Checkpoints and review.** T3 Code attaches checkpoint scope and capture to execution. Git records checkpoint snapshots under hidden refs without adding commits to the user’s branch. The source-control UI can show the changes for a turn, and the server maintains diff queries independently of the agent transcript. A completed provider turn and a completed checkpoint are separate milestones, so the agent can be shown as finished while its diff is still being captured. [Checkpoint capture](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/CheckpointCaptureService.ts) · [Checkpoint Git implementation](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/vcs/GitVcsDriver.ts#L1629) · [Diff query](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/checkpointing/CheckpointDiffQuery.ts) · [Review turn changes](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/user/source-control.md#review-turn-changes)

**Undo.** Rewinding a conversation and restoring workspace files are related operations with distinct checks. T3 Code checks the capability and scope, refuses unsafe shared-workspace file restores, and coordinates native rollback with the checkpoint restore and app projections. If native rollback is needed, the rollback service invokes it before restoring files. A rewind can change which native history remains usable for future continuation. [Checkpoint rollback](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/CheckpointRollbackService.ts#L303) · [Rollback safety tests](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/CheckpointRestoreSafety.test.ts)

**Forks and merge-back.** A fork creates a new app thread linked to a source point. On the first run, T3 Code can resolve that lineage via a native fork where capability, native references, and source state permit it. Otherwise it supplies portable history. Merge-back records a context transfer from a related thread and can feed the result into a later run. Any code integration still happens through ordinary workspace or Git operations. [Fork source policy](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/ThreadForkService.ts) · [Fork dispatch](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L5881) · [Merge-back dispatch](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L6007) · [Launch-time fork resolution](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/Orchestrator.ts#L8789)

## Remote and headless clients

**An environment is the execution authority.** Web, desktop, and mobile display host-owned data. Environment identity is independent of a network route, so a loopback endpoint and a remote address can refer to the same host. The shared connection runtime scopes credentials, subscriptions, and cached state by environment. An environment’s project workspace and provider accounts are resolved on that environment. [Remote architecture](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/internals/remote.md) · [Connection runtime](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/internals/connection-runtime.md) · [Environment auth](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/internals/environment-auth.md)

**Terminal remains a tool.** The host owns PTYs and bounded output history. Clients attach to a terminal and render it independently of the structured conversation. The assistant timeline therefore has its own messages, commands, approvals, and diffs even when a conventional shell is open beside it. [Terminal runtime](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/internals/terminal-runtime.md) · [Terminal manager](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/terminal/Manager.ts)

**Headless ingress shares the domain.** Outside MCP clients can read or launch threads within their access level. T3 Code’s thread CLI can use the same tools. Agent calls, headless commands, scheduled work, and UI interaction can then converge on common services and state, with their own caller scopes. [Outside agents and CLI](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/user/outside-agents.md) · [Orchestration tools](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/mcp/toolkits/orchestrator/tools.ts)

## Legacy migration

T3 Code’s V1-to-V2 cutover copies the previous database once and imports thread information and transcripts into V2. It preserves metadata including workspace and model selection. Old execution graph history, checkpoint and diff history, and the old live session are outside the reconstructed V2 conversation. The first continuation can start a new native conversation using a bounded saved-history handoff. Data from the two app versions can diverge after cutover. [Legacy importer](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/apps/server/src/orchestration-v2/legacy/LegacyV1ThreadImporter.ts) · [Migration behavior](https://github.com/pingdotgg/t3code/blob/106a1e03b73f4a0d114cd7f7de20be2c343c22c1/docs/user/thread-migration.md)

Devcroft already has Git, Review, Resources, terminal, and session-navigation surfaces. Typed runs could connect those to agent work by thread, checkout, and Git base. Worktree preparation and reviewable diffs fit a local-first implementation. Remote connections, schedules, and provider-aware rollback each add distinct storage, lifecycle, and authorization requirements. See [the proposed Devcroft design](05-devcroft-architecture.md#workspace-and-existing-features).
